================================================================================
   RETAIL CONTROL — ARSITEKTUR AUTH & USER MANAGEMENT (DOKUMENTASI LENGKAP)
================================================================================

Dokumen ini menjelaskan secara detail arsitektur, komponen, database schema,
flow end-to-end, dan mekanisme keamanan yang terkait dengan Authentication
dan User Management pada project RetailControl.

Terakhir diperbarui : 2026-02-27 (sinkronisasi Module 01 + 02 + perbaikan minimal)

================================================================================
 1. GAMBARAN UMUM (OVERVIEW)
================================================================================

RetailControl adalah sistem POS (Point of Sale) berbasis Laravel yang dirancang
untuk mengelola operasional retail multi-cabang. Sistem ini menggunakan:

  - Framework        : Laravel 10.x
  - Auth Guard       : Session-based (web guard) dengan Session Storage: Database (tabel sessions)
  - API Auth         : Laravel Sanctum (tersedia, belum digunakan aktif)
  - Hashing          : Bcrypt (via Laravel's 'hashed' cast)
  - RBAC             : Role-Based Access Control custom (bukan package pihak ke-3)
  - Soft Delete      : Ya, pada model User
  - Audit Trail      : Otomatis via Auditable trait + AuditLogger service
  - Multi-Branch     : User terikat ke branch (cabang), kecuali role global

═══════════════════════════════════════════════════════════════════════════════
 8.3 SIMPAN USER BARU (STORE)
═══════════════════════════════════════════════════════════════════════════════

  Request: POST /admin/users
  Middleware: auth → auth.session → active
  Controller: UserController::store()

  Flow:
  1. StoreUserRequest melakukan:
     a. authorize(): Cek permission 'users.create'
     b. rules(): Validasi input:
        - name:     required, max:100
        - username: required, min:3, max:50, regex lowercase+angka+underscore,
                    unique di tabel users
        - email:    nullable, valid email, max:150, unique di tabel users
        - password: required, confirmed, min:8, harus ada huruf + angka
        - role_id:  required, harus ada di tabel roles
        - branch_id: nullable, integer
        - is_active: boolean
     c. withValidator(): Validasi tambahan:
        - Role yang requiresBranch() WAJIB punya branch_id
        - Role yang isGlobal() TIDAK BOLEH punya branch_id

  2. Cek role: jika isGlobal() → set branch_id = null

  3. User::create($data)
     → Password otomatis di-hash oleh Laravel (cast 'hashed')
     → Auditable trait otomatis mencatat ke audit_logs:
       - action: 'create'
       - auditable_type: 'App\Models\User'
       - new_values: semua atribut kecuali password & remember_token

  4. Redirect ke /admin/users + flash message 'User berhasil ditambahkan.'

═══════════════════════════════════════════════════════════════════════════════
 8.5 UPDATE USER (UPDATE)
═══════════════════════════════════════════════════════════════════════════════

  Request: PUT /admin/users/{user}
  Middleware: auth → auth.session → active
  Controller: UserController::update()

  Flow:
  1. Gate::authorize('update', $user) → policy check

  2. UpdateUserRequest melakukan:
     a. authorize(): Cek permission 'users.update'
     b. rules():
        - Sama seperti StoreUserRequest, KECUALI:
        - password: nullable (boleh kosong = tidak diubah)
        - username & email: unique kecuali milik user yang diedit
          (ignore soft-deleted records)
        - is_active: required boolean
     c. withValidator(): Branch validation sama seperti Store

  3. Jika password kosong → unset dari data (tidak di-update)

  4. Jika role global → set branch_id = null

  5. $user->update($data)
     → Auditable trait otomatis mencatat ke audit_logs:
       - action: 'update'
       - old_values: snapshot nilai lama (yang berubah saja)
       - new_values: snapshot nilai baru (yang berubah saja)
       - Kecuali kolom password & remember_token

  6. Redirect ke /admin/users + flash message 'User berhasil diperbarui.'


═══════════════════════════════════════════════════════════════════════════════
 8.6 HAPUS USER (DESTROY)
═══════════════════════════════════════════════════════════════════════════════

  Request: DELETE /admin/users/{user}
  Middleware: auth → auth.session → active
  Controller: UserController::destroy()

  Flow:
  1. Gate::authorize('delete', $user)
     → UserPolicy::delete()
     → Cek permission 'users.delete'
     → TIDAK BOLEH menghapus diri sendiri
     → TIDAK BOLEH menghapus user Super Admin

  2. $user->delete()
     → SOFT DELETE (set deleted_at = now())
     → Data tetap ada di database, hanya ditandai dihapus
     → Auditable trait otomatis mencatat ke audit_logs:
       - action: 'delete'
       - old_values: snapshot semua atribut user

  3. Redirect ke /admin/users + flash message 'User berhasil dihapus.'


═══════════════════════════════════════════════════════════════════════════════
 8.7 NONAKTIFKAN USER (DEACTIVATE)
═══════════════════════════════════════════════════════════════════════════════

  Request: PATCH /admin/users/{user}/deactivate
  Middleware: auth → auth.session → active
  Controller: UserController::deactivate()

  Flow:
  1. Gate::authorize('deactivate', $user)
     → UserPolicy::deactivate()
     → Cek permission 'users.deactivate'
     → TIDAK BOLEH menonaktifkan diri sendiri
     → TIDAK BOLEH menonaktifkan user Super Admin

  2. $user->update(['is_active' => false])
     → User masih ada di database (bukan soft delete)
     → EnsureUserIsActive middleware akan menendang session user tsb
       pada request berikutnya
     → Auditable trait otomatis mencatat ke audit_logs:
       - action: 'update'
       - old_values: {is_active: true}
       - new_values: {is_active: false}

  3. Redirect ke /admin/users + flash message 'User berhasil dinonaktifkan.'

  Perbedaan vs Hapus (8.6):
  - Deactivate: user masih ada, bisa diaktifkan kembali via Edit User
  - Hapus:      soft delete, user "hilang" dari list (tapi tetap di DB)

┌─────────────────────────────────────────────────────────────────────────────┐
│ 9.1 PENCATATAN OTOMATIS (via Auditable Trait)                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  Trait Auditable mendaftarkan 3 event listener di bootAuditable():          │
│                                                                             │
│  EVENT         AKSI                                                         │
│  ───────────   ────────────────────────────────────────────────────────     │
│  created       Catat action='create', new_values = semua atribut            │
│                (kecuali $auditExclude)                                      │
│                                                                             │
│  updated       Catat action='update',                                       │
│                old_values = nilai lama kolom yang berubah,                  │
│                new_values = nilai baru kolom yang berubah                   │
│                (kecuali $auditExclude)                                      │
│                Skip jika tidak ada perubahan yang perlu dicatat             │
│                                                                             │
│  deleted       Catat action='delete', old_values = semua atribut            │
│                (kecuali $auditExclude, termasuk soft delete)                │
│                                                                             │
│  $auditExclude default: ['password', 'remember_token']                      │
│  Dapat di-override per model via property $auditExclude                     │
│                                                                             │
│  SETIAP entry audit berisi:                                                 │
│  - user_id      : siapa yang melakukan aksi (Auth::id())                    │
│  - ip_address   : IP address yang melakukan request                         │
│  - user_agent   : Browser/client info                                       │
│  - created_at   : timestamp kejadian                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  AuditLogger::log(action, auditable, oldValues, newValues)                  │
│  → Untuk aksi yang bukan CRUD Eloquent (contoh: void transaksi)             │
│                                                                             │
│  AuditLogger::logAuth(action, user)                                         │
│  → Shorthand khusus login/logout                                            │
│  → Otomatis menyertakan ip_address di new_values                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ 9.3 MELIHAT AUDIT LOG                                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  Request: GET /admin/audit-logs                                             │
│  Middleware: auth → auth.session → active → permission:audit_logs.view      │
│  Controller: AuditLogController::index()                                    │
│                                                                             │
│  Pengecekan ganda:                                                          │
│  1. RequirePermission middleware → permission 'audit_logs.view'             │
│  2. abort_unless di controller → permission 'audit_logs.view'               │
│                                                                             │
│  Filter yang tersedia (query string):                                       │
│  - auditable_type : filter berdasarkan model (contoh: "App\Models\User")    │
│  - user_id        : filter berdasarkan pelaku aksi                          │

│ MEKANISME MULTI-BRANCH                                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  KONSEP:                                                                    │
│  - Role GLOBAL (super_admin, owner) → branch_id = NULL → akses semua        │
│  - Role NON-GLOBAL (admin_cabang, kasir, accounting)                        │
│    → WAJIB punya branch_id → hanya akses cabang yang ditugaskan             │
│                                                                             │
│  HELPER di User Model:                                                      │
│                                                                             │
│  getAccessibleBranchId(): ?int                                              │
│    → Return NULL jika isGlobal() (berarti: akses semua, jangan filter)      │
│    → Return branch_id jika non-global                                       │
│                                                                             │
│  canAccessBranch(int $branchId): bool                                       │
│    → Return true jika isGlobal() ATAU branch_id cocok                       │
│                                                                             │
│  BranchScoped Trait (untuk model lain seperti Transaction, Product, dll):   │
│                                                                             │
│  scopeForBranch(?int $branchId)                                             │
│    → Jika $branchId = NULL → no filter (return query apa adanya)            │
│    → Jika $branchId = angka → WHERE branch_id = $branchId                   │
│                                                                             │
│  PENGGUNAAN DI CONTROLLER:                                                  │
│    $branchId = auth()->user()->getAccessibleBranchId();                     │
│    Transaction::forBranch($branchId)->get();                                │
│                                                                             │
│  VALIDASI DI FORM REQUEST:                                                  │
│  - Saat membuat/edit user, branch_id WAJIB diisi untuk role non-global      │
│  - Saat membuat/edit user, branch_id TIDAK BOLEH diisi untuk role global    │
│  - Controller UserController menimpa branch_id = null untuk role global     │

================================================================================
 15. CATATAN & PERTIMBANGAN ARSITEKTUR
================================================================================

  1. SUPER ADMIN BYPASS
     Super Admin mendapat akses penuh BUKAN melalui mapping permission,
     melainkan via bypass langsung di User::hasPermission(). Ini berarti
     role super_admin tidak perlu relasi di tabel role_permissions sama sekali.

  2. BRANCH SYSTEM (BELUM LENGKAP — Module 03+)
     Tabel branches belum dibuat. Module 02 tidak membuat tabel branches;
     items dan master data bersifat global (bukan per-cabang).
     branch_id di users tetap BIGINT tanpa foreign key ke tabel branches.
     FK akan ditambahkan pada modul yang memerlukan data per-cabang
     (misalnya Inventory / Module 04).
     CATATAN: Model stub Branch.php sudah dibuat (app/Models/Branch.php)
     agar User::branch() tidak throw "Class not found". Model ini hanya
     berisi fillable dan relasi minimal; tabel dan migration dibuat nanti.

  3. AUDIT LOG IMMUTABILITY
     audit_logs dirancang sebagai tabel append-only. Ini dijaga oleh:
     - Model guard (throw LogicException pada updating/deleting)
     - Tidak ada route/controller untuk mengedit/menghapus audit log
     - Hanya ada kolom created_at (tanpa updated_at)

  4. SOFT DELETE PADA USER
     User yang dihapus tetap ada di database (soft delete) agar:
     - Referensi di audit_logs tetap valid
     - Data historis tidak hilang
     - audit_logs.user relasi menggunakan withTrashed()

  5. PERMISSION CHECK BERLAPIS
     Sistem menggunakan pengecekan berlapis untuk keamanan:
     - Layer 1: Middleware (RequirePermission) untuk filter di level route
     - Layer 2: Gate/Policy (Gate::authorize) untuk filter di level controller
     - Layer 3: Form Request (authorize()) untuk filter di level validasi
     Tidak semua layer digunakan bersamaan, tergantung kebutuhan route.

  6. API ROUTE (SANCTUM)
     Tersedia endpoint GET /api/user yang dilindungi auth:sanctum, namun
     belum digunakan aktif. Sanctum configuration sudah ada di
     config/sanctum.php.

  7. REMEMBER ME
     Fitur "Remember Me" didukung via parameter $remember di
     LoginService::attempt(). Jika true, Laravel akan membuat cookie
     remember_token yang bertahan lebih lama dari session.
